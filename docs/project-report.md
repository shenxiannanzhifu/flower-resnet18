## 题目与目标

项目识别雏菊、蒲公英、玫瑰、向日葵和郁金香，覆盖独立 Python 环境、公开数据整理、统计可视化、手写网络、训练验证、保存加载、测试评估和新图预测。采用命令行程序，不增加网站、数据库或云部署。

PDF 要求手写残差块与 ResNet、使用 PyTorch 训练并展示新图预测，也要求同一项目实际使用 NumPy/Pandas/Matplotlib。具体采用 ResNet-18、五类数据、30 轮训练与版本拆分，是本项目的实现选择；PDF 没有准确率门槛。

## 数据与分析

使用 TensorFlow 官方示例 flower_photos，原包 3,670 张图片，遵守 CC BY 2.0；数据来源、校验与使用条件见 [data.md](data.md)，完整署名保存在 [data-license.txt](data-license.txt)。项目没有直接复制参考项目实现。

图片检查覆盖解码、尺寸、类别、文件/像素哈希及近重复候选。人工规则辅助复核后按重复关系分组，再分层划分，避免已知重复跨集。v0.2.1 最终保留 3,664 张，train/val/test 为 2,564/551/549。保留隔离依据与原图，不宣称已消除全部标签噪声。

## 手写网络与训练流程

`src/model.py` 用 Conv2d、BatchNorm2d、ReLU 等基础组件编写 BasicBlock，计算 `ReLU(F(x) + shortcut(x))`。尺寸和通道相同时直接传递 x；否则以 1×1 卷积和匹配步长投影，保证两支路能够逐元素相加。

ResNet-18 包含四组各两个残差块 [2,2,2,2]，通道为 64/128/256/512，最终自适应平均池化及五类全连接层，参数量 11,179,077。没有调用 torchvision 的完整 ResNet，也未使用预训练权重。

训练使用 logits 与交叉熵，依次清梯度、前向、求损失、backward、SGD step。验证不更新权重，使用 eval 和 inference_mode。按样本数加权统计损失，最后不足一批的样本也保留。

正式配置：seed=42、batch=32、30 epochs、SGD 学习率 0.01、momentum=0.9、weight_decay=0.0005、每 10 轮学习率乘 0.2；普通 FP32。RTX 5060 Laptop GPU 约 8GB，PyTorch 2.8.0+cu128，单进程 DataLoader。完整实验约 14 分钟，不代表其他机器耗时。

按最小验证损失保存最佳模型，checkpoint 同时记录类别、预处理、归一化和配置。先固定模型选择记录并提交为 `98b4018`，再进行独立测试。文件支持推理加载，不支持精确恢复优化器和随机状态续训。

## AI 辅助范围与个人感悟

以下文字按本人要求，由 AI 根据本任务真实对话、日志和提交记录协助整理，供本人审阅。本人提出项目要求、反馈电脑报错、要求修复推送并逐阶段继续，代码编写、命令运行、排查和实验整理主要由 AI 协助完成。这里不将这些工作写成本人独立实现，也不据此宣称本人已经掌握全部代码。

这次项目中，我希望得到一个能逐步理解、能够实际运行、开发过程可以查证的花卉分类项目，所以一开始就要求按版本推进，每完成一阶段再继续下一阶段，并保留真实 Git 提交。实际推进中遇到的阻力，既有环境和工具问题，也有数据质量和模型能力的问题。这些经历给我的一个启发是：完成项目除了写出网络结构，还需要让环境、数据、训练、预测和交付互相配合，每个环节都要有相应的验证。

环境准备就是一个具体例子。本机系统 Python 是 3.14，项目根据可用安装包和 GPU 条件选择 Python 3.12 独立环境及 PyTorch CUDA 12.8 构建。过程中出现了临时目录权限、依赖下载停滞，以及 PyTorch 专用安装源不能提供 Pandas 的问题。AI 协助将常规依赖与 PyTorch 分开安装，对从官方来源下载的安装包核对哈希，最后通过实际 CPU、GPU 运算验证环境。这部分过程值得我借鉴的是：安装完成的提示还不够，依赖能否在目标环境中真实运行也需要检查；环境版本和处理方法应记录下来，方便以后复现。

我直接反馈过的一个问题，是电脑弹出“内存不能为 read”一类报错，并且代码没有成功推送到 GitHub。后续排查记录表明，崩溃的是 Git 的 HTTPS 传输进程，而不是花卉模型读取图片失败。本地提交已经存在，但远程上传没有完成。AI 随后使用隔离的 Python Git 传输工具恢复上传，并重新读取远端提交和标签进行核对，保留了原来的开发历史。系统 Git 的崩溃根因并未因此被宣称彻底修复。这个过程让我更重视区分“本地提交成功”和“远程推送成功”，也提醒我不能只根据一条笼统的错误提示就判断问题出在模型或数据上。

Windows 多进程加载失败时，我也提出过先判断是否有必要解决，再决定下一步。实际诊断定位到进程间管道访问被拒绝，项目最终保留经过验证的 num_workers=0，使用单进程完成正式训练。这项处理没有修复系统权限问题，但确实让本次规模的任务顺利完成。对我而言，这体现了实现过程中的取舍：面对一个问题，应结合它是否影响正确性、实际耗时和当前目标来决定投入，而不是把所有可能的优化都变成必须完成的前置任务。

数据和验证环节同样有具体阻力。项目复核发现了同场景图片跨划分和明显标签噪声，随后通过 v0.2.1 补丁调整已确认的重复分组、隔离问题样本，并保留原始图片及修改依据。正式评估收尾还遇到了 Windows CRLF 与 Git LF 换行转换导致报告哈希校验误报的问题；修复时区分了文本换行差异和真实内容变化，模型二进制仍保持严格校验。这些记录说明，图片能打开、程序能运行并不意味着整个实验就可靠，划分是否泄漏、结果能否追溯以及跨工具保存后是否仍能核验，都需要认真处理。

模型方面，我提出过希望解决未知类别误判和中心裁剪遗漏花朵的问题。实际比较并没有得到“改了就更好”的结果：同一批 551 张验证图片中，中心裁剪准确率为 82.21%，整图输入为 80.94%。因此项目保留中心裁剪默认值，只把整图作为可选方式。未知类别的诊断也显示，八张非花卉合成图都能通过按已知图片分数设置的阈值，简单阈值不能可靠拒绝未知输入。对这次优化，我更愿意保留真实结果和适用边界，而不是把没有验证成功的方案写成已经解决的问题。单张图片的高分与一批有真实标签图片上的准确率，也必须分别说明。

在 AI 协作方面，我明确要求了中文注释、分阶段验收和实际提交，也持续反馈问题并提出改进方向。AI 帮助完成了大量实现和排查工作，但项目能运行不能替代我自己的代码理解。接下来我需要重点练习解释残差连接和维度匹配、训练与验证的区别，以及模型加载时为什么必须同时恢复预处理和类别映射；再通过亲自运行、查看结果和录制视频来检查自己的掌握程度。我希望最终提交的内容既有真实可运行的成果，也能清楚说明哪些已经验证、哪些仍存在限制，以及哪些知识还需要继续学习。
